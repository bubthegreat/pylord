# Gameplay Deviations from lord.js

This document tracks intentional deviations between pylord and the reference Synchronet LORD implementation.

| Deviation | Reason |
|-----------|--------|
| Forest: "no fights left" loops back to the *forest* menu, not town | lord.js's own handler (`:15308-15316`) shows the message and continues its `do...while` loop over the forest menu; it never sets `over = true`. An earlier draft of this task's brief guessed "back to town" -- lord.js's actual behavior wins. |
| Forest in-battle menu: one generic `(S)kill attack` letter instead of lord.js's per-class `D`/`M`/`T`, and no in-battle `(S)tats` view | Explicit simplification requested by this task's brief (`battle_prompt()`, lord.js `:6841-6869`, for the letters being replaced). |
| `Player.skill_uses` (single shared field) vs. lord.js's `levelw`/`levelm`/`levelt` (one per class) | This project's `Player` has one permanent rank per class (`skill_dk`/`skill_my`/`skill_th`, raised by `raise_class` at Turgon's) and one *shared* daily-use counter. Since a player only ever has one class at a time the shared counter is equivalent in play; the daily formula is ported from `wake_up()` (lord.js `:5448-5469`) and the Mystical tiers are gated on both the counter and the permanent rank, exactly as lord.js does (`:7247-7268`). A player who masters a class and switches profession keeps the old rank, which only affects the rankings screen's "Mastered" column. |
| Forest events: 9 of lord.js's up to 16 `look_to_kill()` switch cases (`:14482-15041`) are implemented -- old man escort (0), the old hag (1), find gold (2), Merry Men (3), find gem (4), the pretty/ugly stick (7), the horse trader (8), the fairy blessing (9, simplified) and the purse-snatching troll (13) | Originally only 6 were ported, which meant two thirds of the events that fired resolved silently and players reported seeing no encounters at all. Still skipped, with reasons: case 5 (`flower_garden()` sub-minigame), case 6 (per-class skill training, a large sub-function each), case 10 (`olivia()`, settings-gated off by default in lord.js too), case 11 (`rescue_the_princess()`), case 12 (`find_lost_gold()`, needs the shared multiplayer gold pool this project doesn't model), case 15 (`darkhorse_tavern()`, a full gambling/rumour sub-game). Those fall back to lord.js's own silent case 14. |
| (superseded) Forest events: only 6 of lord.js's up to 16 `look_to_kill()` switch cases (`:14482-15041`) are implemented -- old man escort (case 0), find gold (case 2), Merry Men heal (case 3), find gem (case 4), fairy blessing (case 9, simplified), and "nothing" (case 14) | Brief's explicit "keep scope sane: the 4-6 core events" instruction. Skipped, with reasons: case 1 (old hag heal-for-gem, moderate complexity), case 5 (hammer stone / `flower_garden()` sub-minigame), case 6 (skill-track leveling, depends on Turgon's/Task 11), case 7 (charm-stick RNG), case 8 (horse trading sub-menu, `player.horse` mechanics out of scope), case 10 (`olivia()` easter egg, explicitly settings-gated off by default), case 11 (`rescue_the_princess()`), case 12 (`find_lost_gold()`, depends on a shared multiplayer "forest gold" pool this project doesn't model), case 13 (mega-event troll that can kill the player outright), case 15 (`darkhorse_tavern()`, a full gambling/rumor sub-game). All fall back to "nothing" (same as lord.js's own case 14, silent by design) rather than being individually ported. The overall probability shape (1-in-5 chance any event fires, uniform over 15 or 16 sub-outcomes) is preserved -- an enabled IGM's `forest_event` hook adds its weight alongside those slots. |
| Forest death: gold is discarded outright rather than swept into a recoverable shared "forest gold" pool | lord.js's `save_forest_gold(player.gold)` (`:15070`) feeds a shared multiplayer pool later recoverable via the (also-skipped) `find_lost_gold` event. Not modeled; net effect on the dying player is identical (`gold = 0`, lord.js `:15071`). |
| Forest death penalty is **all** on-hand gold + 10% exp loss, not "half gold" | An earlier draft of this task's brief guessed "lose half gold on hand"; lord.js's actual `look_to_kill()` death handler (`:15070-15072`) zeroes gold entirely and subtracts `exp // 10`. lord.js wins. |
| `daily.maintenance()` is a global once-per-day batch pass, not lord.js's per-player lazy `wake_up()` | Explicit architecture requested by this task's brief (`game_state['last_maint']` guard). Every value/formula (bank interest, forest/player fight counts, skill-uses formula, resurrection) is still ported faithfully from `wake_up()` (lord.js `:5412-5595`); only the trigger mechanism differs. |
| `daily.maintenance()` applies bank interest / skill-use resets to every player unconditionally | lord.js gates most of `wake_up()`'s per-player maintenance on `player.gone < settings.res_days` ("hasn't abandoned the game too long"); this project doesn't model `gone`/`res_days` absence-tracking, so the gate is dropped and maintenance applies to everyone. |
| Forest `(V)iew your stats` routes to the shared `stats` scene, which always returns to `"town"` afterward, not back to `"forest"` | `stats` (Task 8, `pylord/engine/scenes/stats.py`) hardcodes its own return value to `"town"`; out of scope for this task to change. | Forest "you have enough exp to level up" hint (`grant_exp()`, `pylord/engine/game.py`) has no lord.js source text | Searched `reference/lord.js` for any "enough experience"/"go see your master"-style string at the point exp is credited in the forest (`:15107-15112`) -- none exists. lord.js only tells the player via `turgons()`'s own master dialogue (`:15590-15606`) when they actually visit. | Bank (`bank`): no `(T)ransfer` (send gold to another player) | lord.js's transfer (`:16019-16097`) is player-to-player, backed by `find_player()`/`mail_to()` -- explicitly deferred by this task's brief as PvP-adjacent (Task 13). |

| Turgon's `(V)iew rankings` shows the Hall of Honors scene rather than writing a scores file | lord.js's `V` (`:15870-15881`) generates `rank_king()`'s dragon-kill leaderboard into a file and displays it; this port routes straight to the `hall` scene, which renders the same board from `Player.king_count` (this project's `drag_kills`). |

## Deliberate design changes (not fidelity gaps)

The rows above record where this port *differs while trying to match*
lord.js. The two below are changes the owner asked for, made with eyes
open, because a persistent telnet server is played differently from a
once-a-day BBS door call.

| Change | Rationale |
|--------|-----------|
| **Forest-fight capacity is trainable.** lord.js gives every player the same flat allowance each morning (`settings.forest_fights`, reference/lord.js:5428, :5443-5445). Here that figure is the *base*: beating a master adds one permanent fight, and Turgon's new `(E)ndurance` key sells more for gold, each costing a multiple more than the last (`pylord/engine/fights.py`). Only purchases raise that price -- the free point a master grants, and the level that comes with it, never do. The daily reset fills to the trained maximum. | Gives long-lived characters something to spend gold on and makes progression visible in the one resource that actually limits play.
