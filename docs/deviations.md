# Gameplay Deviations from lord.js

This document tracks intentional deviations between pylord and the reference Synchronet LORD implementation.

| Deviation | Reason |
|-----------|--------|
| Forest: "no fights left" loops back to the *forest* menu, not town | lord.js's own handler (`:15308-15316`) shows the message and continues its `do...while` loop over the forest menu; it never sets `over = true`. An earlier draft of this task's brief guessed "back to town" -- lord.js's actual behavior wins. |
| Forest in-battle menu: one generic `(S)kill attack` letter instead of lord.js's per-class `D`/`M`/`T`, and no in-battle `(S)tats` view | Explicit simplification requested by this task's brief (`battle_prompt()`, lord.js `:6841-6869`, for the letters being replaced). |
| `Player.skill_uses` (single shared field) vs. lord.js's `levelw`/`levelm`/`levelt` (one per class, recomputed daily from `skillw`/`skillm`/`skillt`) | This project's `Player` model has one skill-rank field per class (`skill_dk`/`skill_my`/`skill_th`) and one *shared* daily-use counter. Since a player only ever has one class, "shared" and "per-class" are behaviorally identical; formula ported from `wake_up()`, lord.js `:5448-5469`. |
| Forest events: only 6 of lord.js's up to 16 `look_to_kill()` switch cases (`:14482-15041`) are implemented -- old man escort (case 0), find gold (case 2), Merry Men heal (case 3), find gem (case 4), fairy blessing (case 9, simplified), and "nothing" (case 14) | Brief's explicit "keep scope sane: the 4-6 core events" instruction. Skipped, with reasons: case 1 (old hag heal-for-gem, moderate complexity), case 5 (hammer stone / `flower_garden()` sub-minigame), case 6 (skill-track leveling, depends on Turgon's/Task 11), case 7 (charm-stick RNG), case 8 (horse trading sub-menu, `player.horse` mechanics out of scope), case 10 (`olivia()` easter egg, explicitly settings-gated off by default), case 11 (`rescue_the_princess()`), case 12 (`find_lost_gold()`, depends on a shared multiplayer "forest gold" pool this project doesn't model), case 13 (mega-event troll that can kill the player outright), case 15 (`darkhorse_tavern()`, a full gambling/rumor sub-game). All fall back to "nothing" (same as lord.js's own case 14, silent by design) rather than being individually ported. The overall probability shape (1-in-5 chance any event fires, uniform over 15 or 16 sub-outcomes) is preserved. |
| Forest death: gold is discarded outright rather than swept into a recoverable shared "forest gold" pool | lord.js's `save_forest_gold(player.gold)` (`:15070`) feeds a shared multiplayer pool later recoverable via the (also-skipped) `find_lost_gold` event. Not modeled; net effect on the dying player is identical (`gold = 0`, lord.js `:15071`). |
| Forest death penalty is **all** on-hand gold + 10% exp loss, not "half gold" | An earlier draft of this task's brief guessed "lose half gold on hand"; lord.js's actual `look_to_kill()` death handler (`:15070-15072`) zeroes gold entirely and subtracts `exp // 10`. lord.js wins. |
| `daily.maintenance()` is a global once-per-day batch pass, not lord.js's per-player lazy `wake_up()` | Explicit architecture requested by this task's brief (`game_state['last_maint']` guard). Every value/formula (bank interest, forest/player fight counts, skill-uses formula, resurrection) is still ported faithfully from `wake_up()` (lord.js `:5412-5595`); only the trigger mechanism differs. |
| `daily.maintenance()` applies bank interest / skill-use resets to every player unconditionally | lord.js gates most of `wake_up()`'s per-player maintenance on `player.gone < settings.res_days` ("hasn't abandoned the game too long"); this project doesn't model `gone`/`res_days` absence-tracking, so the gate is dropped and maintenance applies to everyone. |
| Forest `(V)iew your stats` routes to the shared `stats` scene, which always returns to `"town"` afterward, not back to `"forest"` | `stats` (Task 8, `pylord/engine/scenes/stats.py`) hardcodes its own return value to `"town"`; out of scope for this task to change. A player who checks stats mid-forest-visit lands in the Town Square instead of back in the forest. |
| Forest "you have enough exp to level up" hint (`grant_exp()`, `pylord/engine/game.py`) has no lord.js source text | Searched `reference/lord.js` for any "enough experience"/"go see your master"-style string at the point exp is credited in the forest (`:15107-15112`) -- none exists. lord.js only tells the player via `turgons()`'s own master dialogue (`:15590-15606`) when they actually visit. This announcement is an invented, undisguised UX addition so players aren't left guessing; actual leveling still only happens at Turgon's (Task 11). |
| Fairy blessing (`_event_fairy`) always rolls a flat 3-way outcome, not lord.js's horse-conditional 3-or-4-way | lord.js's blessing roll is `random(3 + (player.has_horse ? 0 : 1))` (`:14826`) -- a 4th outcome (a horse companion) only exists when the player *doesn't* already have one. This port drops the horse-companion outcome entirely (see the "forest events implemented" row above -- horse trading is out of scope), so the roll is always a flat `random(3)` over the other three regardless of `player.horse`. |
| Shops (`weapons`/`armor`): no in-shop `(V)iew stats` | lord.js's `Y`/`V` in-shop key shows the player's Stats screen without leaving the shop (`show_stats()`, `king_arthurs()`/`abduls_armour()`). Dropped -- Stats is already one keypress away at Town Square, and every scene in this codebase (`forest.py`'s own `V`) already accepts that visiting Stats mid-errand returns to town, not back to the errand. |
| Shops: full item list shown every time the shop menu redraws, not only on a one-off `(L)ook` press | Neither shop's original lord.js asset (`ARTHUR`/`BUYWEP`/`ABDUL`/`BUYARM`, loaded via `lrdfile()`) is present in this repo -- same convention as `town.py`'s own reconstructed menu. |
| Healer (`healer`): always returns to `"town"`, regardless of whether it was entered from the Town Square or the Forest | Same simplification already established by `stats.py` (see the Forest `(V)iew your stats` row above) -- `GameCtx` has no "return to caller" concept for this project's scene graph. lord.js's `healers()` has no such ambiguity; it's a plain function call that returns to whichever screen called it. |
| Bank (`bank`): no `(T)ransfer` (send gold to another player) | lord.js's transfer (`:16019-16097`) is player-to-player, backed by `find_player()`/`mail_to()` -- explicitly deferred by this task's brief as PvP-adjacent (Task 13). |
| Bank: no thief "steal from the bank" (`2` key, `has_fairy` gate) | Gated on `player.clss === 3 && player.has_fairy` (lord.js:16119-16153); the fairy-capture flag isn't modeled on this project's `Player` (see the Forest fairy-event deviation above). This is the only "robbery" mechanic anywhere in `ye_old_bank()` -- there is no rob-another-player feature to defer; it's simply out of scope for the reason above. |
| Bank: no "leaving the bank" Amulet random event | lord.js:16162-16220, gated on `player.amulet` -- no equivalent field anywhere in this project's `Player` model (`combat.py`'s module docstring already notes amulet handling is project-wide out of scope). |
| Turgon's Training: `(Q)uestion` shows `needstr1`/`needstr2` when the player is *over* the exp threshold, not under it | An earlier draft of this task's own brief described the flavor quotes as appearing "when not ready". lord.js's actual `ask()` (`:15577-15610`) shows them only when `player.exp > trainer.need` (the "you don't need me anymore" flavor); under-threshold shows a generic "need about N more experience" line instead, and `attack_master()`'s own under-threshold response is a separate comedic sequence that never references `needstr1`/`needstr2` at all. lord.js wins over the brief's paraphrase. |
| Turgon's Training: no `(V)iew rankings` (Heroes Of The Realm) | lord.js's `V` (`:15870-15881`) writes a dragon-kill leaderboard (`rank_king()`/`drag_kills`); `Player` has no `drag_kills` field and no dragon-kill tracking exists anywhere in this project yet (Task 13+). |
| Turgon's Training: no `raise_class()` class-skill-rank increase on a win | lord.js:15803 (function body `:10578-10771`) -- a real mechanic (permanent skill rank +1 per win, up to a class-mastery/"choose a new profession" branch at rank 40) that depends on the `levelw`/`levelm`/`levelt` daily-counter fields this project already collapsed away (`forest.py`'s deviation 3). Not requested by this task's brief; deferred, not silently dropped. |
| Turgon's Training: no `tournament_check()` | lord.js:15805 (body `:3362-3420`) -- an end-game dragon-kill tournament trigger; no `drag_kills`/PvP-kill/tournament-settings modeling exists yet. |
| Inn: `W`/`D`/`V` route to the standalone `mail`/`news`/`stats` scenes, which end back at `"town"`, not back at the Inn | Same "detour scene always returns to town" simplification already established by `healer.py`/`stats.py` for the Forest's `V`iew stats detour -- `GameCtx` has no "return to caller" concept. lord.js's `red_dragon_inn()` calls these as plain sub-functions and falls back into its own menu loop afterward (reference/lord.js:9945-9997). |
| Inn: no `C`onverse (Dark Horse Tavern gambling mini-game) or `M`announce (everyone-sees free-text broadcast) | reference/lord.js:8459-8574 (`converse()`) and :9397-9432 (`announce()`). `C` mirrors the same-spirit skip already recorded for the Forest's `darkhorse_tavern()` random event (see the forest-events row above); neither is requested by this task's brief or covered by any requested test. |
| Inn's bartender (`T`): no elixir shop (`G`, gem currency), no rename (`C`, gold), and no bribe-to-attack-sleepers (`B`) | reference/lord.js:8090-8437. Only the Violet/Seth gossip lines and the level-12 dragon hint survive (`pylord/engine/scenes/inn.py`'s `_bartender`). The elixir shop and rename are flavor/economy features not requested by this task's brief; the bribe (`attack_in_inn()`, lord.js:7979-8089) is PvP, explicitly deferred to Task 13b (left as a `TODO(13b/PvP)` comment in the source). |
| Inn's bard menu (`H`'s `F`): the "someone else already married Seth Able" homewrecking sub-branch is a flat status line, not the full seduce-and-compare-charm-then-mail-the-spouse mini-game | reference/lord.js:9322-9386. Low value relative to its complexity (a third-party mail side-effect); out of scope for this task. |
| Violet/Seth Able marriage: no `player.divorced` cooldown check | reference/lord.js:9496-9499 (Violet) -- this project's `Player` model has no `divorced` field; player-to-player marriage/divorce isn't modeled at all yet (see the Mail/Conjugality rows below), so there's nothing for a cooldown to gate against. |
| Inn: no hidden "JENNIE" codeword mechanic | Searched `reference/lord.js` for any Inn-specific codeword handling -- the only `JENNIE` hit (`JENNIE GARTH`, lord.js:4794) is part of the unrelated celebrity-name-rejection easter egg in character-name validation (`check_name()`), not an Inn mechanic. This task's brief speculated such a mechanic might exist ("port if present ... else document deviations row"); it doesn't. |
| Violet's `kiss()` success branch bug-fixed to credit `player.exp`, not lord.js's literal `player.ext` | reference/lord.js:9647 -- almost certainly a typo (no other code anywhere reads or writes `player.ext`, and the very same line's message text promises "You receive N experience!", exactly like every sibling tier). This project's established convention treats a provable transcription bug as fixable rather than a "feature" to preserve (see e.g. `terminal.py`'s module docstring on the `` `r`` background-code bug); the *intended* behavior (credit real exp) is ported instead. |
| No global NPC-marriage `state` table; `married_to_violet`/`married_to_seth` stored as `game_state` key/value rows | lord.js keeps a singleton `state` object (`state.married_to_violet`/`state.married_to_seth`, reference/lord.js:2494-2495) shared by every player; this project has no equivalent table, so `pylord/engine/npc_state.py` reuses the existing `game_state` key/value table (already used by `GameCtx.news()`'s `'day'` counter) for the same purpose. |
| Mail: no player-to-player romantic reply-mail mini-game (wink/kiss/dinner/invite-to-room/propose-marriage, each with its own charm-gated reply screen) | reference/lord.js:3820-4209 (`wink_mail()`/`kiss_mail()`/`dinner_mail()`/`sleep_mail()`/`marry_mail()`), reached via `compose_mail()`'s romantic branch (lord.js:5012-5177) -- this is lord.js's *real* mechanism for setting `player.married_to` (a genuine player-to-player marriage, reference/lord.js:4096). This task's brief scopes the Mail scene's async-effect channel to non-romantic stat deltas (`gold`/`gems`/`exp`/.../`player_fights`, see `pylord/engine/effects.py`) with no romance-specific effect type, and the Inn scene (this task's actual romance surface) already covers Violet/Seth Able marriage. Out of scope; `player.married_to`/`conjugality.py`'s player-to-player rows are consequently unreachable until a later (PvP-adjacent) task adds this mini-game. See `mail.py`'s module docstring. |
| Mail compose: no word-wrap, no "quote the message you're replying to", and a fixed "(no message)" placeholder instead of lord.js's five random one-liner "derps" for a blank first line | reference/lord.js:3179-3301 (`write_mail()`). Line-wrapping and reply-quoting depend on file-based state (`quote<id>.lrd`) this project's line-oriented `TermIO.readline()` doesn't model; the placeholder text is a simpler, equally-inert substitute for lord.js's flavor-text random pick. |
| Mail is applied/shown exactly once, at login (before the Town Square), rather than lord.js's continuous `check_mail()` polling on every menu redraw | reference/lord.js:2300-2360, called from dozens of call sites throughout `main()`/`red_dragon_inn()`/etc. This project's sessions are long-lived telnet connections (not lord.js's one-shot BBS door calls), and this task's brief explicitly asks for login-time application; mail that arrives *during* an active session is shown at the *next* login instead of immediately. See `server.py`'s wiring and `mail.py`'s module docstring. |
| List Warriors sorts by experience descending, not "level desc" | An earlier draft of this task's own brief described the ranking as "level desc"; lord.js's actual `generate_rankings()` (reference/lord.js:6580-6689, used by both `list_players()` and `slaughter_others()`'s own `L`) sorts strictly by `exp` descending (line 6612). lord.js wins over the brief's paraphrase, this project's established convention (see e.g. `combat.py`'s or `training.py`'s module docstrings). |
| Hall of Honors reachable only as a List Warriors submenu (`H`), not from any Town Square letter | lord.js's own dragon-kill leaderboard (`rank_king()`, reference/lord.js:15612-15647) is nested inside Turgon's Training's `V`iew rankings key -- which `training.py` (Task 11) deliberately didn't implement (see that module's own deviations row above), leaving no town-square letter that reaches it. Exposed instead as this task's brief suggests ("expose via List Warriors submenu"). |
| News: no random daily "happenings" flavor line | reference/lord.js:3040-3055/3085 (`happenings[random(happenings.length)]`, written once per day by `create_log()`). This project's daily maintenance pass (`pylord/engine/daily.py`, Task 10) doesn't write one, and extending it is out of this task's scope; `daily_news` here only ever holds real gameplay events. |
| Effect channel (`pylord/engine/effects.py`/`pylord/engine/limits.py`): `charm`/`forest_fights`/`player_fights` capped at 32,000 | lord.js's own `add_hp()`/`add_str()`/`add_def()` helpers (reference/lord.js:6458-6480) cap those three stats at 32,000; lord.js has no equivalent helper for `charm` or an explicit `player_fights` (`pvp_fights`) cap. | Inn's bard menu (`H`'s `F`, "married to me" reunion line): one fixed line instead of lord.js's 8-way flavor pool | reference/lord.js:9294-9319 (`switch (random(8))`: "I love you too, honey!" / a peck on the cheek / "duty calls" / "we'll have time tonight" / drowned out by the crowd / "don't want to bother him" / "after work, you're mine" / a wink). | PvP (`pvp.py`): "Examine/Write In The Dirt" (`E`/`W`) graffiti-wall minigame dropped | reference/lord.js:16517-16590+ (`slaughter_others()`'s own `E`/`W` cases) -- an entire separate multiplayer graffiti feature (reads/writes an external `dirt.lrd`/`GetConversation dirt` file, unrelated to combat) this task's brief never asks for.
